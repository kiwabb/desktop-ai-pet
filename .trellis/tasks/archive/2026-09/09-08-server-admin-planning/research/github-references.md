## 针对本项目的架构建议（具体方案见 design.md 评审稿）

独立 Web 管理前端 → 同源管理 HTTP API（候选 `/admin/v1`）→ 现有 PostgreSQL、Redis 和业务服务。

- 保留 FastAPI、psycopg 与已有业务事务，不为后台换 ORM。管理查询增加明确的分页、筛选、权限和字段裁剪。
- 管理员认证与 control/node 设备认证分开设计；浏览器会话可采用 HttpOnly Cookie 并补齐 CSRF 防护，具体方案在设计阶段确认。
- 账号/设备创建及撤销从 CLI 提取可复用业务逻辑，新增接口调用同一逻辑。凭证发放操作需要明确一次性展示、下载与丢失后重新签发规则。
- 不直接复用 `/v1/control/ws` 给浏览器。其 Origin 拒绝规则服务于现有设备通道，管理列表首期可使用分页 HTTP 与有界轮询。
- 节点租约有效只证明节点通道仍活跃，不代表模型、控制通道或客户端全部功能健康。Redis 不可读应呈现未知。
- 运行详情通过 run_id 关联工具调用与事件。时长可依据已有开始/终态事件推导；缺失事件时明确标记不完整，不补造时间。
- 用户追加 DSH 链路追踪需求后，Token 采集提升为首期追踪能力；成本估算与配额仍后置，旧运行不回填伪造数据。直接交互参考详见 [DeepSeek Harness 追踪调研](deepseek-harness-tracing.md)。
- 当前模型在 `AgentService.start` 中初始化；用户已确认首期支持配置编辑，因此必须处理持久化、密钥保护、配置版本、实例重建与在途运行，不能把一个表单当作配置管理闭环。详细发布规则见 [设计稿](../design.md)。
- 现有工具有副作用，后台不得提供无条件“重试全部”。如要重试，先明确已提交结果、幂等与人工对账策略。
- 后续提示词在线编辑会引入服务端与单机提示词差异，须修订双模式当前要求一致的契约，而非悄悄修改单侧。

## 首期用户路径建议

1. 登录 → 总览 → 失败运行 → 事件时间线 → 工具调用详情，完整定位一次失败。
2. 账号 → 创建设备 → 一次性领取凭证 → 桌面接入 → 后台看到节点租约 → 撤销 → 验证访问失效。
3. 账号 → 会话或待办 → 查看真实状态 → 返回列表 → 刷新后保持筛选与数据一致。

信息架构候选：总览、账号与设备、会话与运行、模型配置、待办与提醒、工具目录、系统与审计。图标沿用 Lucide；高信息密度页面强调可读性、层次和稳定导航，动效不干扰排障。
